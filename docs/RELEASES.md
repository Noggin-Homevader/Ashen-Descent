# Publishing a game update

The launcher installs **published GitHub Releases** of this repository that carry a release manifest
(`ashen-manifest.json`) and a packaged build. Commits, branches, tags without a release, draft releases and
GitHub's automatic "Source code" archives are never treated as playable updates.

## Release checklist

1. Put the new game build in `game/app/` (today that is the single-file HTML build, `game/app/index.html`).
2. Bump `"version"` in `game/game.json` using [semantic versioning](https://semver.org): `2.0.1` for fixes,
   `2.1.0` for new content, `3.0.0` for changes that break saves. Use a prerelease suffix (`2.1.0-beta.1`) for
   test builds.
3. Add a `## 2.0.1` section at the top of `game/CHANGELOG.md`. It becomes the release notes in the launcher.
4. Optional local check: `node tools/package-game.js && node tools/verify-release.js dist/game`
5. Merge the change to `main` (or push it there).
6. The **Game release** workflow sees a version that has no release yet. It runs the tests, packages the game,
   verifies the files and **publishes** release `vX.Y.Z`. Launchers pick it up the next time they open.

Versions with a prerelease part (`2.1.0-beta.1`) are published as GitHub prereleases. Launchers only offer them
to players who switch on **Include test builds**. Pushing to `main` without changing the version releases
nothing. Game releases are published with "latest" turned off, so the repository's latest release is always the
launcher and its download link never changes.

To pull a bad release, unpublish it (turn it back into a draft) or delete it. Launchers that already installed it
keep it until a newer version is published; they never downgrade automatically.

## The release manifest

`ashen-manifest.json` is generated by `tools/package-game.js` from `game/game.json`. Schema 1:

```json
{
  "schema": 1,
  "name": "ashen-descent",
  "version": "2.0.0",
  "releaseNotes": "Markdown shown in the launcher",
  "minLauncherVersion": "1.0.0",
  "builds": [
    {
      "os": "any",
      "arch": "any",
      "runtime": "web",
      "file": "AshenDescent-2.0.0-any-any.zip",
      "size": 7506406,
      "sha256": "64 lowercase hex characters",
      "executable": "index.html",
      "args": [],
      "requiredFiles": ["index.html"],
      "preserve": []
    }
  ]
}
```

| Field | Meaning |
|---|---|
| `schema` | Always `1` for this format. Launchers skip manifests with a schema they do not understand. |
| `name` | Must be `ashen-descent`. |
| `version` | Semantic version. Must equal the release tag without its `v` (tag `v2.0.0` → `2.0.0`). |
| `releaseNotes` | Optional Markdown. If empty, the launcher shows the GitHub release body. |
| `minLauncherVersion` | Optional. Older launchers skip this release and tell the player to update the launcher. |
| `builds[].os` | `windows`, `macos`, `linux`, or `any`. |
| `builds[].arch` | `x64`, `arm64`, `x86`, `arm`, or `any`. |
| `builds[].runtime` | `web`: an HTML5 build that the launcher opens in its built-in game runtime. `native`: a real executable. |
| `builds[].file` | Name of the `.zip` asset attached to the same release. |
| `builds[].size` | Exact size of that asset in bytes. Must also match the size GitHub reports for the asset. |
| `builds[].sha256` | SHA-256 of that asset. Downloads that do not match are deleted and retried. |
| `builds[].executable` | Path of the program (or `index.html` for web builds), relative to the install folder. |
| `builds[].args` | Arguments passed to the game on every launch. |
| `builds[].requiredFiles` | Files that must exist after unpacking. The executable is always required. |
| `builds[].preserve` | Player files that live **inside** the install folder and must survive updates, e.g. `["saves/", "settings.ini"]`. A trailing `/` means a folder. Not needed for web builds, whose saves live in the launcher's profile folder. |

**How a build is chosen.** For the player's computer the launcher prefers, in order: an exact OS and CPU match;
the same OS with `arch: "any"`; on Apple Silicon Macs, an `x64` macOS build (it runs through Rosetta); and
finally an `any`/`any` build. Only one build per OS/CPU pair is allowed.

**How a release is chosen.** The launcher reads the 30 most recent releases. It ignores drafts and tags that are
not `v<semver>` (so `launcher-v1.0.0` releases are never mistaken for the game), and ignores prereleases unless
test builds are switched on. It sorts the rest by semantic version, not by date, and takes the newest one that
has a valid manifest, a build for this computer, and that build's asset with the right size. A broken newest
release is skipped in favour of the newest working one, and the skip is written to the launcher log.

**Packages.** A `.zip` with the game's files at its root. The launcher refuses archives that contain absolute
paths, `..`, drive letters, symbolic links, duplicate names, encrypted entries or ZIP64 records. It also checks
every file's CRC-32 and size. `tools/package-game.js` writes archives that meet all of these rules and re-checks
them with the launcher's own code.

## Adding native builds later

If the game ships native executables (for example a Unity or Godot export), give each its own entry in
`game/game.json`:

```json
{ "os": "windows", "arch": "x64", "runtime": "native", "appDir": "build/windows-x64",
  "executable": "AshenDescent.exe", "args": ["--launcher"], "requiredFiles": ["AshenDescent.exe", "AshenDescent_Data/globalgamemanagers"],
  "preserve": ["Saves/"] }
```

`package-game.js` produces one zip per entry. Players on other systems keep receiving the `any`/`any` web build
as long as it is listed.
